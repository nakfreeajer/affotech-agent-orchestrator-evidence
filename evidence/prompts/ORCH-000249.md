PROBLEM
The current BrowserRelay/Architect trigger successfully wakes the Architect, but its payload is only `verify & next`.
The Architect can therefore generate the next AFFOTECH Executor prompt in ChatGPT without publishing that prompt into nakfreeajer/affotech-agent-relay.
The local watcher then remains on the previous LATEST_ARCHITECT_PROMPT until Rony or another Architect manually publishes the new prompt.

This defeats the primary purpose of the Orchestrator: automatic Architect -> Executor continuation.

GOAL
Make the Architect -> AFFOTECH relay handoff automatic without scraping or parsing the Architect response DOM.

PERMANENT CONTRACT
1. While an Executor/Codex child is alive, Architect must remain dormant. No Architect trigger is sent while state=RUNNING.
2. After the Executor actually exits and its result is captured/preserved, send exactly one Architect trigger for that completed result.
3. The Architect trigger must explicitly instruct the Architect that a next Executor prompt shown only in ChatGPT is NOT issued.
4. If the Architect creates a next AFFOTECH Executor instruction, before its final response it must:
   - publish a fresh immutable prompt.md and manifest.json to nakfreeajer/affotech-agent-relay main;
   - embed the complete prompt in the manifest;
   - use the correct parent publication and source/invariant authority;
   - advance relay/current/LATEST_ARCHITECT_PROMPT.json;
   - read back and verify the new pointer/hash.
5. If the Architect correctly decides that no next Executor task should be issued (for example a genuine human-auth/manual-action blocker), it must not advance the AFFOTECH relay.
6. BrowserRelay must NOT read, scrape, classify, or parse Architect assistant response text. responseDomRead remains false.
7. The watcher determines continuation only from the authoritative AFFOTECH relay pointer advancing to a new valid publication.
8. Exactly-once remains mandatory: one Architect trigger per completed Executor result; one execution per AFFOTECH publication.
9. Browser/composer send failure may retry delivery of the same Architect trigger only. It must not rerun Executor.
10. No wall-clock duration may classify a live Executor or Architect task as failed.

TRIGGER PAYLOAD
Replace the bare `verify & next` doorbell with a deterministic instruction equivalent to:

`verify & next. Complete the handoff before replying: if you create a next AFFOTECH Executor instruction, publish it as a fresh immutable prompt+manifest to nakfreeajer/affotech-agent-relay main, advance relay/current/LATEST_ARCHITECT_PROMPT.json, and verify read-back. A next prompt shown only in chat is NOT issued. If no next Executor task is appropriate, do not advance the relay. Do not read or scrape the Architect response DOM.`

The exact wording may be normalized for safe transport, but all semantics above are mandatory.
