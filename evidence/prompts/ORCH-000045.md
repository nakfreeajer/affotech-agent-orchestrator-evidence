Supervisor Orchestrator and AFFOTECH relay are distinct protocol families.

Supervisor Orchestrator canonical control family:
- ORCH-* message IDs
- DISPATCH-* dispatch IDs
- private Orchestrator GitHub evidence/control records

Protected external AFFOTECH relay family:
- PUB-* relay identifiers

Rules:
1. Do not access AFFOTECH or nakfreeajer/affotech-agent-relay in this milestone.

3. It MUST NOT translate PUB-* to ORCH-* or DISPATCH-*.
4. It MUST NOT translate ORCH-* / DISPATCH-* to PUB-*.
5. It MUST NOT normalize, migrate, reinterpret, import, fetch, or derive authority across protocol families.
6. A bare AFFOTECH-family PUB-* identifier presented where an Orchestrator canonical message/dispatch identity is required must fail closed as a foreign protocol family.

DURABLE CORRELATION IDENTITY — GOVERNING INVARIANT
The ORCH-000043/ORCH-000044 qualification proved that repeated payload text alone is insufficient to reconcile a specific ambiguous external attempt.

For any ambiguity reconciliation that claims a specific external effect was or was not applied, compatibility/reconciliation logic must require durable target-bound correlation evidence sufficient to distinguish the intended attempt from historical same-content effects.

The generic correlation contract must be able to bind, at minimum:
- operation/intent identity;
- source messageId and dispatchId where applicable;
- target/resource identity or registered authority/registration identity;
- payload/mutation SHA-256 or equivalent immutable effect identity;
- durable pre-attempt external-state boundary reference and hash/identity where applicable;
- attempt lineage/ordinal or equivalent attempt identity.

Rules:
- repeated payload equality alone is insufficient;
- timestamp alone is insufficient;
- current composer/DOM/external state alone is insufficient when historical same-content effects can exist;
- missing required correlation evidence => INSUFFICIENT_CORRELATION_EVIDENCE;
- insufficient correlation never authorizes retry;
- no blind retry remains permanent;
- historical records may remain readable without being rewritten, but compatibility/readability does not imply they are correlation-capable for a new reconciliation conclusion.

IMPLEMENTATION CONTRACT

A. COMPATIBILITY REGISTRY
Create a dependency-free ES-module compatibility registry with pure deterministic interfaces sufficient to:
- identify/check the expected Orchestrator protocol family from caller context;
- validate exact supported schemaVersion for an exact record/pointer kind;
- distinguish supported, reserved-not-yet-supported, unknown, version-unsupported, and foreign-family outcomes;
- expose machine-readable fail-closed reason codes;
- never rewrite or normalize the supplied record.

The exact exported function names are implementation detail, but tests and report must identify them.

B. PROTOCOL FAMILY
Represent at least:
- ORCHESTRATOR_GITHUB as the current executable family;
- AFFOTECH_PUB_EXTERNAL as a protected foreign symbolic family.

Do not read AFFOTECH to populate the foreign family.
The registry must not provide any translate(), migrate(), normalize(), or cross-family conversion behavior.

C. CURRENT ID GRAMMARS
For Orchestrator dispatch compatibility:
- canonical message identity is ORCH-* under the existing accepted grammar;
- canonical dispatch identity is DISPATCH-* under the existing accepted grammar.

A bare PUB-* relay identifier cannot satisfy either field.
GH-PUB-* evidence publication identifiers remain permitted in fields whose existing Orchestrator evidence contract permits publication IDs.

D. VERSION HANDLING
At this milestone:
- schemaVersion "1.0" is the supported current/historical version for the registered existing kinds;
- any other version is unsupported unless the registry explicitly marks a future kind RESERVED_NOT_YET_SUPPORTED;
- do not infer compatibility from numeric closeness;
- do not parse "1.1" as "1.0 compatible";
- do not silently add missing schemaVersion.

E. DURABLE CORRELATION EVALUATOR
Add a pure deterministic correlation-evidence evaluator used by reconciliation-facing logic.

It must be able to return at least:
- CORRELATION_SUFFICIENT
- INSUFFICIENT_CORRELATION_EVIDENCE
- CORRELATION_MISMATCH

For an external-effect reconciliation to be correlation-sufficient, require durable identity for the specific attempt, target, source lineage, payload/effect hash, and pre-attempt boundary/reference/hash where the reconciliation class requires external-state comparison.

Do not retroactively mutate historical intents.
A readable legacy record may still return INSUFFICIENT_CORRELATION_EVIDENCE for reconciliation capability.

F. CURRENT WATCHER / CLOSED-LOOP INTEGRATION
Wire the registry into the accepted worker-relay resolver/watcher/closed-loop read path only at deterministic validation boundaries.

At minimum:
- current/immutable dispatch compatibility is checked before candidate eligibility;
- unsupported/unknown/foreign-family dispatch fails closed with zero send;
- durable worker result compatibility is checked before it can advance result processing;
- Architect-trigger/reconciliation compatibility checks fail closed on unsupported schema/kind;
- any reconciliation path that would infer a specific ambiguous external attempt from repeated/non-unique content must require the correlation evaluator;
- missing correlation => no retry and no send.

Do not change GITHUB_DISPATCH_LOCATOR_V1 payload grammar in this milestone.
Do not change the fixed Architect doorbell text.
Do not perform any live browser operation.

G. BACKWARD-COMPATIBILITY BOUNDARY
