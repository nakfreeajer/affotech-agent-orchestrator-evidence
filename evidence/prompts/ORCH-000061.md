D. EVENT IDENTITY

Use a stable format such as:
EVT-<zero-padded-sequence>-<bounded-hash-prefix>

Do not use randomness.
Caller-supplied createdAt may be recorded but timestamp alone must not establish uniqueness.

E. PUBLISH EVENT ALGORITHM
Implement publishEvent(request):

1. read one fresh current index plus blob SHA, or explicit ABSENT;
2. validate index structure/project/head invariants;
3. allocate sequence = nextSequence;
4. read/validate the current head event when one exists;
5. build exact candidate using accepted project-event semantics and current head linkage;
6. create the immutable event candidate once;
7. CAS-create/update PROJECT_EVENT_INDEX from the observed index/blob state so it references the exact candidate and advances indexRevision/nextSequence/head;
8. return PUBLISHED only after durable readback proves the index references the exact immutable candidate.

If immutable create or index CAS is ambiguous:
- return AMBIGUOUS;
- return a bounded reconciliation descriptor;
- perform no second create/CAS in the call;
- do not grant retry authority;
- do not treat an orphan candidate as canonical.

A stale/conflicting CAS must never overwrite a newer index.

F. EVENT PUBLICATION RECONCILIATION
Implement reconcilePublishEvent(request) as read-only.

Distinguish at minimum:
- PUBLISHED_RECONCILED: exact candidate is the canonical head or is provably linked into the canonical chain;
- NOT_PUBLISHED_SAFE: candidate exists or not, but is not canonical and no ambiguous relation remains;
- CONFLICT: same producerEventKey or intended sequence is canonically occupied by an incompatible event;
- INCONCLUSIVE: evidence cannot be safely related.

Reconciliation performs no write and does not authorize same-iteration retry.

Exact duplicate producerEventKey + identical canonical payload already present may be returned as idempotently published only when the canonical chain proves the exact same event identity. A differing payload under the same producerEventKey is a hard conflict.

G. ONE-REF EVENT RANGE READ
Implement readEventsAfter(cursor, options).

It must:
1. read exactly one current branch HEAD/ref;
2. read PROJECT_EVENT_INDEX at that ref;
3. walk the immutable previous-event links from head using readJsonAtRef(..., sameRef);
4. stop at the exact cursor event or chain origin;
5. reverse the collected records into oldest-to-newest order;
6. validate every sequence/link/hash/project/event contract;
7. return the bound sourceRef and a contiguous event array;
8. support an explicit bounded maxEvents batch size;
9. fail closed on gaps, cycles, malformed links, foreign project, hash mismatch, missing cursor, or a cursor not on the canonical chain.

Never mix refs during one range read.
No list-directory heuristic may define chronology.

For an empty cursor, reading from origin is allowed only within maxEvents. If history exceeds the bound, return BATCH_LIMIT_REACHED with a safe continuation boundary rather than silently skipping events.
