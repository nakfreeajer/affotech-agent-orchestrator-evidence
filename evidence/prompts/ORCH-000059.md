F. LEASE ACQUISITION
Implement acquireMutationLease(request) using the accepted MUTATION_LEASE evaluator and deterministic requiredLease descriptor from ORCH-000058.

Required request context must include:
- hostInstanceId / hostGenerationId
- requiredLease descriptor
- nowMs
- requested expiry/TTL under explicit bounded policy
- exact expected project/repository/branch.

Algorithm:
1. read fresh current index and its blob SHA, or a well-defined ABSENT state;
2. validate all currently active entries and evaluate overlap/conflict using accepted MUTATION_LEASE semantics;
3. if conflicting ACTIVE lease exists => DENIED/CONFLICT with no write;
4. allocate deterministic next leaseEpoch from the observed index state;
5. derive a deterministic MUTATION-LEASE-* leaseId from bound host/action/lineage/epoch identity without randomness/wall-clock reads beyond caller nowMs;
6. project exact ACTIVE revision 1 with previousRecordSha256=null;
7. create the immutable revision-1 record once;
8. activate it only by CAS create/update of MUTATION_LEASE_INDEX using the observed state/blob SHA;
9. return ACQUIRED only when durable readback proves the index references the exact immutable candidate.

If immutable record creation or index CAS is ambiguous:
- return AMBIGUOUS;
- provide a bounded reconciliation descriptor;
- do not create/acquire again in the same call;
- do not silently treat an orphan immutable candidate as active authority.

Concurrent acquisition safety depends on the index CAS. No stale-index overwrite.

G. LEASE ACQUISITION RECONCILIATION
Implement reconcileMutationLease(request) read-only for ambiguous acquisition.

It must read a fresh current index and exact candidate revision and distinguish at minimum:
- ACQUIRED_RECONCILED: exact candidate is active in index;
- NOT_ACQUIRED_SAFE: candidate is not active and no conflicting active lease claims the requested scope;
- CONFLICT: another active overlapping lease now owns the scope;
- INCONCLUSIVE: evidence cannot be safely related.

No reconciliation outcome performs a write or grants retry in the same iteration.
The runner may only reconsider a fresh acquisition on a later iteration after a new durable snapshot.

H. LEASE RELEASE
Implement releaseMutationLease(request) using the accepted immutable release projection.

Require:
- exact active lease/index entry;
- exact holder/lineage/scope/envelope;
- caller nowMs;
- exact prior immutable record SHA.

Algorithm:
1. read fresh current index + exact current immutable active record;
2. validate/evaluate exact lease;
3. project immutable next revision state RELEASED;
4. create the immutable release revision once;
5. CAS-update the index using observed blob SHA to remove that lease from activeLeases and advance indexRevision;
6. return RELEASED only after durable readback proves the lease is no longer active and exact release revision exists.

If release-record create or index CAS is ambiguous:
- return AMBIGUOUS / leaseReconciliationRequired=true;
- do not issue a second release in the call;
- never change the transport result;
- never authorize resend/retry.
